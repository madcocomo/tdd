## 暂定标题
代码，本来就很适合当 AI 的 Harness

最近 AI 智能体讨论里，Harness Engineering 这个说法越来越常见。它讨论的并不是模型参数本身，而是模型外面那层工程结构：工具、环境、状态、校验和反馈回路。说得简单一点，就是怎么把模型放进一个可执行、可验证、可反馈的闭环里。

如果顺着这个定义往下想，会得到一个很值得程序员注意的反转：所谓 Harness，很多时候恰恰就是我们最熟悉的代码。代码会把任务拆成显式步骤，交给运行时执行，允许重复运行、调试、测试和回滚。对于“让 AI 解决问题”这件事来说，它不是最后那层包装，而是让任务开始收敛的中间层。

这在数字任务上尤其明显。直接让 LLM 从一堆数据里生成统计结论，最常见的结果是文字像样，数字不对。可如果把任务改成“先写 Python，再执行，再生成报表”，结果通常会可靠得多。原因不是 prompt 更花哨，而是计算被交给了解释器，过程可以复查，结果可以核对。

这也不是零散技巧。已经有不少研究比较过这两种路径：一种让模型直接在自然语言里一步步算，另一种让模型先把解法写成程序，再交给解释器执行。前者更自由，后者更受约束，而在很多数值和多步推理任务上，后者通常更准。这里真正起作用的，不是“代码”这个词本身，而是程序带来的可执行和可检查结构。

数学里也能看到同样的思路。陶哲轩谈 AI 与数学形式化时提到，更稳的做法往往不是让模型直接输出自然语言证明，而是先把问题写进形式语言，再交给工具检查或推进。这个例子不需要展开太多，它在这里只说明一件事：当任务被放进一种更严格的中间表示时，错误更容易暴露，结果也更容易站得住。

从这个角度再看“软件会被智能体替代”或者“软件会变成即抛型产物”这些说法，就会发现它们只说对了一半。AI 辅助软件开发的确是现在进展最快的领域之一，但软件之所以先爆发，不是因为它更简单，而是因为软件行业本来就已经有最成熟的一套 Harness：语法、编译、解释、测试、diff、review、CI、回滚。模型一旦接上这套结构，效果当然更容易先在这里显现出来。

所以对普通程序员来说，未来更重要的问题，不只是软件怎么给人用，而是软件怎么给 AI 用，怎么让 agent 更容易理解、调用、试错、验证和恢复。与此同时，很多过去不值得专门软件化的小场景，现在也可能因为一层很薄的程序外壳，被改造成 AI 可执行、可检查的闭环，从而长出新的应用。
