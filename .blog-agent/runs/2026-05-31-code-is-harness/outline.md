## 结构提案

### 1. 开头：为什么现在大家都在谈 Harness
**作用：** 用一个很短的开头把问题立起来。

要点：
- AI 智能体讨论慢慢聚焦到 Harness Engineer。
- 这个词现在说法很宽，有人几乎把它理解成“除了模型之外的一切”。
- 但各种说法里有一个稳定共性：Harness 负责把模型放进一个**可执行、可验证、可反馈**的闭环里。

建议篇幅：80-120 字

---

### 2. 转折：把问题从“Harness 是什么”拉到“代码本身就是 Harness”
**作用：** 这是全文中心转折，也是前半篇最重要的反转。

要点：
- 真正的全景不是“AI 生成代码”，而是：
  - `AI 生成代码 -> 代码解决问题`
- 如果目标是“AI 解决某个问题”，那代码本身就不只是结果，而是一种 Harness。
- 因为代码把开放式任务压成了更收敛的结构：
  - 步骤显式
  - 可执行
  - 可重复
  - 可测试
  - 可调试
- 这里形成的反转是：所谓 Harness，并不只是一个新潮名词；很多时候，它恰恰就是程序员早就熟悉的代码与软件结构。

建议篇幅：120-170 字

---

### 3. 例子一：数据 / 报表 / Python 中间层
**作用：** 用最直观的例子把论点落地。

要点：
- 很早就有人发现，LLM 直接从一堆数字里“生成报表”，很容易写得像样但不可靠。
- 如果改成“先写一段 Python 去读取数据、聚合、统计、生成结果”，正确性会明显提升。
- 这里改进的关键，不是 prompt 更花哨，而是多了一层代码 Harness：
  - 计算被交给解释器
  - 过程可以重复执行
  - 结果可以校验
- 可以顺手提一下 PAL / PoT 这类工作，说明这不是零散经验，而是研究里也反复出现的结构。

建议篇幅：140-180 字

---

### 4. 例子二：数学 / 形式化语言 / Tao
**作用：** 给一个更高门槛但结构相同的例子。

要点：
- 在 AI + 数学的实践里，更可靠的路径也不是让 LLM 直接吐自然语言证明。
- 而是先把命题写进 Lean 这类形式化语言，再在形式系统和工具约束下推进证明。
- Tao 提到过一个很重要的实践判断：
  - theorem statement 要由人生成或严格复核；
  - proof 则可以更多交给自动化工具。
- 这和“先写代码再执行”是同一个结构：
  - 先把问题压进一个可检查的中间表示。

建议篇幅：140-180 字

---

### 5. 到这里，再回看今天很流行的一种判断
**作用：** 把熟悉的行业叙事放进新的框架里重看，让它服务后面的反转判断。

要点：
- AI 辅助软件开发是进展最快的领域之一。
- 因此越来越多人会顺势觉得：
  - 软件会被智能体直接替代；或者
  - 软件会退化成被智能体临时生成的“即抛型”产物。
- 这类说法有现实基础，但它只看到了“AI 生成代码”这一半，没看到代码本身也在承担 Harness 的作用。

建议篇幅：80-120 字

---

### 6. 拉回判断：软件行业为什么会成为 AI 最快落地的地方
**作用：** 回答全文最重要的判断，但不单独展开成长篇背景分析。

要点：
- 软件行业 AI 应用快，不是因为软件更简单，或者更不值得人做。
- 恰恰相反，正因为软件行业天然就有最成熟的一套 Harness，AI 才最容易先在这里长出来：
  - 语法
  - 编译/解释
  - 测试
  - diff
  - review
  - CI
  - 回滚
- 所以未来 AI 与代码更可能是深度协作，而不是简单替代。

建议篇幅：110-150 字

---

### 7. 落到程序员：这意味着什么
**作用：** 收到你已经明确提出的两点，不额外加“总结升华”。

要点：
1. 未来更重要的问题，不只是软件怎么给人用，而是软件怎么给 AI 用。
2. 原本不值得软件化的微小场景，可能因为加上一层很薄的软件 Harness，而突然变得值得，从而长出新的 AI 应用。

建议篇幅：80-120 字
