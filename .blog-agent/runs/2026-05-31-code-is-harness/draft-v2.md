# Draft V2（重新修订，案例开头版）

## 暂定标题
先让 AI 写代码，再让代码说话

把一份 CSV 和一句“帮我做个统计报表”扔给 LLM，得到的结果经常很像真的：有标题，有小结，有数字，甚至还有趋势判断。唯一的问题是，数字常常是编的。很多人第一次认真用大模型碰数字任务，差不多都会撞上这个坑。后来大家慢慢学会一个更稳的做法：别让它直接给答案，先让它写一段 Python 去读数据、计算、出表，再让程序跑出结果。

这个改法看起来只是 prompt 变了一下，其实背后变的是结构。原来是让模型直接从开放式文本跳到结论；现在是让它先产出一个可执行的中间层，再把计算交给解释器，把结果交给校验。过程能重跑，错误能定位，结果能复查。过去几年里，已经有不少研究反复验证过这一点：在数值和多步推理任务上，让模型先写程序再执行，通常比让它完全靠自然语言硬算更准。

如果把这个现象翻译成最近常说的 Harness Engineering，其实意思很简单：模型要想稳定干活，不能只靠自己“想”，还得被放进一个能执行、能校验、能返回反馈的结构里。有人把 Harness 讲得很宽，几乎等于模型之外的一切。但对这篇文章来说，更重要的是抓住它最稳定的部分：约束、执行、验证、反馈。

顺着这条线再往下看，就会出现一个很有意思的反转：所谓 Harness，很多时候恰恰就是程序员最熟悉的代码。因为代码会把任务拆成显式步骤，交给运行时执行，允许重跑、调试、测试和回滚。对“让 AI 解决问题”这件事来说，代码不只是被生成的对象，它本身就是把问题收束起来的一层结构。

数学里其实也有同样的味道。陶哲轩谈 AI 与数学形式化时提到，更稳的路线往往不是让模型直接给出自然语言证明，而是先把问题写进形式语言，再交给工具检查或推进。这个例子在这里只起一个旁证作用：代码也好，形式语言也好，它们共同做的事情都是把任务放进一个更容易检查的中间层。

到这里再回头看那种“软件会被智能体替代”或者“软件会变成即抛型产物”的说法，就比较容易看清它的问题了。AI 辅助软件开发确实是现在进展最快的领域之一，所以才会有这种判断。但这类说法只看到了 AI 在写代码，没看到软件行业同时也是最早把 Harness 修完整的行业。语法、编译、解释、测试、diff、review、CI、回滚，这些东西不是软件的旧包袱，而是 AI 今天最需要的支撑面。

这对普通程序员的意义也很直接。第一，未来软件怎么给 AI 用，可能会比软件怎么给人点按钮用更重要。第二，那些原来不值得软件化的微小场景，现在可能因为一层很薄的代码外壳，就被改造成 AI 可执行、可验证的闭环，从而长出以前不存在的新应用。
